# Notepad macOS menu bar evaluation and prototype

13 November 2026. Recommendation: ship a small native SwiftUI macOS app in **1.1**, using `MenuBarExtra` with `.window` style and the existing reminder data layer. Keep **1.0.2** focused on the iOS maintenance release. This change supplies a local prototype, not a compiled or release-ready Mac app. No version, production configuration, App Store record, or upload workflow was changed.

The intended interaction is Edmund's Snippets-style reference: click an icon, see the open board, add a line, and complete a reminder without opening a full application window. Apple's [MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra) supports a popover-like window and menu-bar-only operation through `LSUIElement`. It is available from macOS 13; this prototype deliberately targets macOS 14.

The repository currently targets **iPhone only** (`TARGETED_DEVICE_FAMILY = 1`), so the existing compatible Mac download would be “Designed for iPhone,” rather than necessarily “Designed for iPad.” `HUMANS.md` records compatible Mac availability enabled, but does not establish current usage or Mac QA. Apple distinguishes both labels and restricts these compatible iOS downloads to Apple silicon. See [iPhone/iPad apps on Mac](https://support.apple.com/en-asia/guide/app-store/fird2c7092da/mac) and [availability controls](https://developer.apple.com/help/app-store-connect/manage-your-apps-availability/manage-availability-of-iphone-and-ipad-apps-on-macs-with-apple-silicon).

Catalyst allows only AppKit APIs explicitly available to Catalyst; an `NSStatusItem` bridge is not a simple unconditional AppKit import into the iOS target. Any separately loaded AppKit bundle would need its own supported-API, signing and review investigation. See [Apple's Catalyst documentation](https://developer.apple.com/documentation/UIKit/mac-catalyst). Safari's [Add to Dock](https://support.apple.com/en-ie/104996) is a useful interim Mac entry point, but web APIs do not supply the native menu bar extra.

Confirm the canonical host before adding Mac OAuth/magic-link redirects. The prototype uses no hardcoded web host or callback URL.

**Shared-code audit.** These findings are a source review, not a macOS compilation result. The target uses an explicit file list so future iOS-only additions under `Shared` cannot silently enter the Mac build.

| `ios/Shared` file | macOS status and prototype treatment |
| --- | --- |
| `AppConfig.swift` | Foundation only; included unchanged. Reads Supabase configuration from `Bundle.main` Info.plist keys. Its App Group property is lazy and unused by the Mac prototype. |
| `Reminder.swift` | Foundation model, shared session types and JSON/date handling; included unchanged. Depends on the JWT helper in `ReminderIntentSupport.swift`. |
| `ReminderStore.swift` | Foundation/URLSession actor; included unchanged. Owns REST reads, acknowledged writes, capacity checks, identity/cache protections and optional token refresh. It contains widget snapshot data but imports neither WidgetKit nor ActivityKit. Injecting app-local defaults and memory credentials avoids requiring the iOS App Group. |
| `SharedSessionStorage.swift` | Foundation + Security, both on macOS; included unchanged to satisfy store types. The custom Keychain implementation assumes the configured iOS sharing group. The Mac adapter supplies memory credentials instead; do not use that default group query unconfigured. |
| `ReminderIntentSupport.swift` | Foundation helpers for JWT IDs, title matching and spoken strings, despite its name; no AppIntents dependency. Included unchanged for `JWTUserID`. |
| `ReminderBoardLimits.swift` | Foundation wrapper around `LockScreenLineBudget`; included unchanged after guarding that dependency. |
| `LockScreenLineBudget.swift` | Previously unconditional UIKit (`UIFont`, `UIScreen`). This change guards its import, geometry measurement and cache update methods with `#if os(iOS)`. iOS keeps its existing code. macOS uses the existing six-line fallback and never measures a Mac display or overwrites phone preferences. Constants and `LockScreenMarqueePolicy` remain portable. |
| `LiveActivityPolicy.swift` | Pure Foundation policy; portable unchanged, but excluded because the Mac popover does not need it. |
| `ReminderAttributes.swift` | Imports ActivityKit and conforms to `ActivityAttributes`; excluded. If later added to a shared Mac source group, guard the ActivityKit import/type with `#if os(iOS)` and separate any needed pure presentation helpers. |
| `ReminderLiveActivityController.swift` | ActivityKit lifecycle and activity authorization/token behavior; excluded. Keep behind an iOS-only source boundary or `#if os(iOS)`, not a no-op duplicate Mac controller. |
| `PrivacyInfo.xcprivacy` | Resource, not Swift. Included in the Mac app. It already declares app-local UserDefaults access; its broader collection declarations must be reconciled with the actual Mac release and SDK privacy report. |

There are **no WidgetKit imports in `ios/Shared`**. WidgetKit itself supports macOS; the existing `ios/Widget` target also contains an ActivityKit Live Activity and phone-specific families/layouts, so sharing that entire extension would be incorrect. Native desktop/Notification Center widgets need a separate macOS extension with supported families, timeline loading, App Group and credential access. iPhone widgets on the Mac through Continuity are another route, with different execution behavior; they do not create a menu bar app. See [WidgetKit](https://developer.apple.com/documentation/WidgetKit) and [preparing widgets for additional platforms](https://developer.apple.com/documentation/widgetkit/preparing-widgets-for-additional-contexts-and-appearances). Widgets are deferred from this prototype.

The Supabase client is actually in **`ios/App/AuthSessionClient.swift`**, not `Shared`. It is platform-neutral and included directly, without copying or moving it. `AuthManager.swift` is intentionally excluded: UIKit foreground notifications, `PushTokenRegistrar`, Apple credential monitoring, phone capacity publication, shared-session coordination and Live Activity cleanup make it a poor minimal Mac dependency. Likewise the Mac target excludes AppDelegate, background phone tasks, iOS views and the iOS widget extension. The single shared Swift edit is the line-budget guard; the iOS target sources and dependencies are unchanged.

**Prototype behavior and boundaries.** `ios/Mac/NotepadMacApp.swift` owns one `MacReminderModel` for the application lifetime and presents `MacReminderView` inside `.menuBarExtraStyle(.window)`. `LSUIElement = YES` hides the Dock app presence; the footer has an explicit quit action. The UI uses neutral foregrounds and blue tint, with no red/orange styling. Existing iOS copy is reused exactly where applicable, including “New reminder”, “Send Sign-In Link”, “Use a Sign-In Link Instead” and “Use an Existing Password”. Suggested Mac-specific copy, included in the prototype for Edmund to tweak: “Sign-in code” for code entry, “Could not complete that action. Please try again.” for errors, and “Quit Notepad” for quitting.

The live board lists only open reminders, uses the shared sort order, adds with Return or the plus button, and completes via a row/checkbox-like circle. Writes become visible only after the store acknowledges them. Operations are serialized; failed adds preserve the draft, duplicate in-flight actions are disabled, and sign-out clears the board/cache. A toolbar refresh and Command-R are available. Initial refresh and a 30-second loop run with the popover view task. This is polling, **not Supabase Realtime**; view retention/closing, sleep/wake and reconnect behavior need Mac QA. Offline mutations are not queued. Errors use the generic message above without exposing raw server responses in the UI.

The Mac uses the existing six-line fallback as a conservative creation limit, but displays every open row returned by the service, including boards larger than six. It does not fetch or update `lock_screen_prefs`. For 1.1, read the phone-derived capacity from Supabase and settle the behavior when no phone has published a preference; do not infer the phone's available space from a Mac monitor. Server ownership/quotas remain authoritative.

**Authentication and sync.** The target inherits the same project-level Debug/Release `Config.xcconfig` mechanism as iOS and substitutes `SUPABASE_URL` and `SUPABASE_ANON_KEY` into its own Info.plist. `AppConfig` and `AuthSessionClient` consume those keys unchanged. There are no embedded environment credentials and no service-role client. No config secret files were read or changed for this task.

The prototype implements existing-account email OTP (`signInWithOTP`, `shouldCreateUser: false`, then `verifyOTP(type: .email)`) and the existing email/password flow through the same auth client. The email buttons reuse the iOS sign-in-link labels; the Mac prototype completes this flow by entering a code. The hosted email template must contain `{{ .Token }}` for a user to enter a code. The repository documents magic-link emails, so this prerequisite is **not verified**. No email templates were rewritten and no hosted provider changes were made. A tester with an existing password can use the password path without changing the template. Do not assume an existing Apple-only user has a password. See Supabase's [Swift OTP request](https://supabase.com/docs/reference/swift/auth-signinwithotp) and [verification](https://supabase.com/docs/reference/swift/auth-verifyotp).

Native Sign in with Apple is a 1.1 requirement, not implemented in the prototype. Use AuthenticationServices/SwiftUI's Apple sign-in button on macOS, request an identity token with a hashed nonce, and send the token and original nonce to Supabase `signInWithIdToken`. Enable the Apple capability/entitlement on the selected Mac App ID and confirm its token audience is allowed in the Supabase Apple provider. Preserve identity/account linking, cancellation, credential-state checks and revocation/deletion behavior from the iOS design. A separate Mac bundle ID needs provider/signing configuration; universal purchase does not configure Supabase automatically. See [Supabase native Apple sign-in](https://supabase.com/docs/guides/auth/social-sign-in/auth-apple). Account deletion/export/support and provider parity are release work as well.

The SDK owns session persistence in its Keychain and refreshes on demand. The Mac controller copies only an access token and expiry to an in-memory `SessionCredentialStorage` for `ReminderStore`; its refresh token is deliberately empty. That prevents two independent refresh owners from rotating the same refresh token. Reminder caching uses sandbox-local `UserDefaults.standard`. The SDK refresh token is never stored in preferences. Across Macs and iPhones, the Supabase user/account is the sync identity, **not shared Keychain storage**.

For a future native Mac widget, add a provisioned App Group and Keychain access group to both Mac targets, align the group and service/account names, and test the sandboxed signed builds. The current custom iOS storage uses a non-synchronizable, device-only item; it does not transfer a session from iPhone to Mac. macOS Keychain access-group behavior also requires selecting the Data Protection Keychain where appropriate; audit `kSecUseDataProtectionKeychain` before reusing the custom storage. No sharing entitlement is necessary for this single-process prototype. See [Apple's Data Protection Keychain key](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain) and the pinned SDK's [Keychain storage](https://github.com/supabase/supabase-swift/blob/v2.54.1/Sources/Auth/Storage/KeychainLocalStorage.swift).

For 1.1 Realtime, use the same Supabase project and user JWT, subscribe to that user's `reminders` changes, and refetch through `ReminderStore` after invalidation. Keep RLS as the security boundary; a subscription filter is not authorization. Reauthenticate the channel on token refresh, remove it on sign-out/account switch, and refetch after subscription/reconnect and wake to recover missed changes. Preserve serialization and identity checks while requests are suspended. The existing `AuthSessionClient` does not expose Realtime, so add that capability deliberately rather than introducing another refresh-owning auth client. See [Supabase Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes).

**App Store identity and entitlements.** For the recommended universal purchase, add macOS to the **same App Store Connect app record** and ship the Mac target with the **same bundle ID** as iOS. Platforms share the app record identity/SKU and have platform-specific builds and metadata. Free pricing does not remove the need to decide this identity. A separate Mac record requires a distinct bundle ID and independent listing/review; it can still use the same Supabase backend but is not automatically part of universal purchase. Apple says separate records cannot simply be merged later. See [adding platforms](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-platforms/) and [distribution identity](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution).

The prototype deliberately uses `systems.edmundlim.NotepadMacPrototype` to avoid colliding with a compatible iOS installation while testing. It is a local identifier, **not a new registered or submitted app**. Before any distribution, switch to the selected production identity, test migration/coexistence with the existing compatible download, and confirm how its Mac availability transitions in App Store Connect. Do not assume equal bundle IDs migrate sandbox contents or Keychain sessions automatically. No production Mac app icon is supplied yet.

The Mac entitlements enable `com.apple.security.app-sandbox` and **`com.apple.security.network.client`** for outgoing Supabase HTTPS/WebSocket connections. No incoming network server, APNs, Apple sign-in, App Group or shared Keychain entitlement is added to this prototype. `LSUIElement` is an Info.plist flag, not an entitlement. The Mac App Store requires sandboxing; actual release work includes signing/provisioning, privacy review, artwork/screenshots and account flows. Developer ID distribution would require its own signing/notarization process and is not configured here. See [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox) and [outgoing connections](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.network.client).

Launch at login should be an explicit user setting backed by `SMAppService.mainApp.register()` / `unregister()` on macOS 13+, reflecting `status` and directing users to Login Items settings if approval is needed. Do not register automatically on first launch. This is deferred from the prototype; test from an installed, signed app, including disable/re-enable and relaunch. See [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice).

The prototype's Return, Command-R and Command-Q shortcuts act in the app/popover; they are not a global “open board” shortcut. For 1.1, decide whether a global shortcut is essential, then evaluate a maintained hotkey registration implementation and its sandbox/permission behavior. SwiftUI `.keyboardShortcut` alone does not supply global hotkey registration or a public programmatic `MenuBarExtra` presentation binding. If reliable global toggling is required, an AppKit `NSStatusItem`/`NSPopover` host around the same SwiftUI view is a fallback to evaluate on Mac. No global keyboard monitoring or Accessibility permission is requested in this prototype.

**Build and demonstration on a Mac.** Use Xcode 27 with its Swift 6 toolchain, XcodeGen and the existing locally prepared config mechanism. The project retains its existing Swift language setting; this task does not migrate the whole shared codebase to Swift 6 strict-concurrency mode. Linux has neither Xcode nor XcodeGen here, so no native compilation, project generation or screenshots are claimed.

Exact requested build command, from the repository root:

```sh
cd ios && xcodegen generate && xcodebuild -project LazyMansReminders.xcodeproj -scheme NotepadMac -destination 'platform=macOS' build CODE_SIGNING_ALLOWED=NO
```

For a deterministic demo output location, from `ios/` after generation:

```sh
xcodebuild -project LazyMansReminders.xcodeproj -scheme NotepadMac \
  -configuration Debug -destination 'platform=macOS' \
  -derivedDataPath /tmp/notepad-mac-demo build CODE_SIGNING_ALLOWED=NO
open /tmp/notepad-mac-demo/Build/Products/Debug/NotepadMac.app --args -demo
```

To capture the demo without opening the menu bar popover, launch a new Debug instance with an absolute PNG path (use the app's container for sandboxed builds):

```sh
open -n -W /tmp/notepad-mac-demo/Build/Products/Debug/NotepadMac.app --args \
  -demo -snapshot "$HOME/Library/Containers/systems.edmundlim.NotepadMacPrototype/Data/notepad-popover.png"
```

On launch, the DEBUG-only snapshot mode renders a fixed 380 × 420-point popover at scale 2 in light and dark appearance, writes `notepad-popover.png` and `notepad-popover-dark.png`, then quits. The destination directory must already exist and be writable by the app. The background approximates the popover material with the window background color and rounded corners; this is a view render, not a capture of the system popover chrome. Release ignores `-snapshot`.

Alternatively select `NotepadMac`, Debug, My Mac in Xcode and add `-demo` under Run → Arguments. If macOS requires a locally signed executable to launch, run through Xcode with development signing. The unsigned command verifies building, not provisioning or Keychain access. Live sign-in needs a correctly configured, signed local build and reachable Supabase; do not paste config values into logs or the handoff.

`-demo` is compiled only under `#if DEBUG`. It creates four sample rows in a separate in-memory store before initializing any auth client, real reminder store, defaults, Keychain or runtime configuration: “Water the sample plant”, “Read the sample book”, “Book dentist for Thursday” and “Pay electricity bill”. Add and complete work locally; relaunch resets the samples, polling is skipped, and sign-out is hidden. The build system still expects its normal config file, but the running demo needs no valid Supabase credentials. Release ignores the argument and contains no demo store or sample fixtures. Use `-snapshot` as above or click the menu bar note icon to capture screenshots.
